## Components

**Homeport server** (`src/server`) is a single Node process under pm2. It serves the dashboard and API on 7070, receives webhooks on 9000 and exports metrics on 9101. It does not proxy any app traffic.

**Caddy** is the only HTTP router. Every tunnel sends every hostname to Caddy on 8080, and Caddy matches on the Host header. Homeport generates the Caddyfile and reloads Caddy through its admin API.

**cloudflared** keeps an outbound connection from the Mac to Cloudflare's edge. Homeport generates one ingress file per tunnel that sends each of its hostnames to Caddy, and restarts the tunnel only when that file changes.

**pm2** supervises everything: apps, Caddy, tunnels, monitoring and Homeport itself. Homeport talks to pm2 through its CLI (`pm2 jlist`, `start`, `reload`) rather than its programmatic API, which keeps it compatible across pm2 versions.

**Prometheus and Grafana** are optional, started by Homeport with generated configuration and provisioned dashboards.

## Server layout

```
src/
  shared/types.ts         types shared by server and browser
  server/
    index.ts              start-up: load state, start listeners and loops
    app.ts                Fastify: CSRF guard, auth, errors, static UI
    config.ts store.ts    defaults, paths, db.json with serialized atomic writes
    lib/                  exec (spawn, stream, env hygiene), validators (Zod), events, restarts
    services/
      deploy.ts           queue, pipeline, rollback, polling
      apps.ts sites.ts    app and domain lifecycle, validation, side effects
      caddy.ts            Caddyfile generator, validation, reload
      cloudflared.ts      tunnels, ingress generator, DNS routes, login
      cloudflareApi.ts    DNS record deletion via the Cloudflare API
      pm2.ts              process listing and control
      webhooks.ts         public webhook listener
      notify.ts           Discord and Telegram
    monitoring/
      exporter.ts         prom-client metrics
      configs.ts          prometheus.yml, alert rules, grafana.ini, provisioning
      dashboards.ts       Grafana dashboards built in code
      service.ts          start/stop, status, range queries
      alerts.ts           alert forwarding and a Prometheus-free fallback watcher
    routes/               thin HTTP layer over the services
web/src/                  React dashboard
```

Services emit events (`deploy:finished`, `webhook:received`, `config:changed`) on an in-process bus. Metrics, notifications and Prometheus reloads subscribe to those events, so the deploy pipeline does not know about any of them.

## A deploy, step by step

![Deploy pipeline](/diagrams/deploy-pipeline.drawio.svg)

1. A trigger (webhook, poll or button) calls `queueDeploy`. Each app has its own queue: if a deploy is running, the new request replaces any waiting one, so a burst of pushes produces at most one follow-up deploy.
2. `checkout` clones or fetches only the configured branch and resets hard to it, or to a specific commit for rollbacks.
3. `detectProject` reads the lockfile and `package.json` to choose install, build and start commands, unless the app overrides them.
4. Install runs without `NODE_ENV=production` so build tools from dev dependencies are present. Every step runs in its own process group with a timeout that kills the whole tree.
5. A pm2 ecosystem file is generated and the app is started or reloaded.
6. `waitHealthy` polls pm2 and the port. It fails fast on `errored`, `stopped`, or three restarts.
7. On failure with rollback enabled, steps 2 to 6 run again for the last successful commit.
8. `deploy:finished` is emitted for metrics and notifications.

## Changing a domain

1. The request is validated with Zod.
2. The change is applied to the in-memory state.
3. The full Caddyfile is generated and run through `caddy validate`. If Caddy rejects it, the in-memory state is restored and the error returned. The running Caddy never sees a bad file.
4. State is saved; side effects follow: DNS route, Caddyfile write and reload, ingress rewrite, tunnel restart if its routes changed.
5. Side-effect failures, such as Cloudflare being unreachable, are returned as warnings. The domain is saved and *Re-apply config* retries.
