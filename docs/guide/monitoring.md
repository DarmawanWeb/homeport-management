# Monitoring and alerts

![Monitoring](/screenshots/monitoring.png)

## Turning it on

**Monitoring, Turn on monitoring** starts three processes under pm2, all bound to `127.0.0.1`:

| Process | Port | Role |
|---|---|---|
| `hp-prometheus` | 9090 | Scrapes every 15 s, keeps 30 days, evaluates alert rules |
| `hp-grafana` | 3300 | Two provisioned dashboards, opened at `/grafana/` through Homeport |
| `hp-node-exporter` | 9100 | CPU, disk I/O, network, filesystems |

Homeport also enables Caddy's HTTP metrics. It probes the installed Caddy once to pick `metrics { per_host }` (2.9 and newer) or the older `servers { metrics }`.

![Metrics flow](/diagrams/monitoring.drawio.svg)

## What is collected

See the [metrics reference](/reference/metrics) for the full list. In short: whether each app answers, unplanned restarts, CPU and memory per process, deploy counts and durations, webhook results, request rate, status codes and latency per hostname, and tunnel connections to Cloudflare.

## Alert rules

| Alert | Fires when | Severity |
|---|---|---|
| AppDown | an app does not answer on its port for 2 minutes, outside a deploy | critical |
| AppCrashLoop | more than 3 unplanned restarts in 10 minutes | warning |
| AppHighMemory | an app uses more than 1.5 GB for 10 minutes | warning |
| DomainUpstreamDown | nothing answers behind a domain for 3 minutes | warning |
| TunnelDown | a tunnel process is not running for 2 minutes | critical |
| TunnelDisconnected | a tunnel runs but has no edge connection for 5 minutes | critical |
| CaddyDown | Caddy cannot be scraped for 2 minutes | critical |
| HighErrorRate | more than 5% of a host's requests return 5xx for 5 minutes | warning |
| HostDiskAlmostFull | the apps volume is over 90% full | warning |
| HostHighMemory | memory is over 92% used for 15 minutes | warning |
| HostHighCpu | CPU is over 90% busy for 15 minutes | warning |

::: tip Unplanned restarts
pm2's restart counter also rises on every deploy and manual restart. Homeport opens a one-minute "expected" window around those actions and only counts restarts outside it, so a busy deploy day does not page you.
:::

## Notifications

**Settings, Notifications** takes a Discord webhook URL and/or a Telegram bot token and chat ID. Messages are sent for:

- successful deploys
- failed deploys and rollbacks
- alerts firing, and again when they resolve

Without Prometheus, a built-in watcher still reports apps that stop answering for 90 seconds, so notifications work on the smallest setup too.

## Grafana

Dashboards are provisioned from files generated by Homeport, so they always match the metric names. Edits made in the Grafana UI are overwritten on the next start; copy a dashboard to keep changes.

### Opening Grafana and Prometheus from anywhere

Both keep listening on `127.0.0.1` only. Homeport proxies them at **`/grafana/`** and **`/prometheus/`** on whatever address you use for the dashboard: the Mac itself, `http://mac-mini.local:7070` on your LAN, or a public hostname. The same sign-in protects them; a browser without a session is sent to the sign-in page and back.

There is no second login. Grafana runs in auth-proxy mode and trusts the username Homeport sends from loopback: Homeport **admins are Grafana admins**, **viewers are Grafana viewers**. Headers a client sends itself are dropped, and Homeport's session cookie never reaches Grafana.

Through the proxy, Prometheus's `/-/reload`, `/-/quit` and `/api/v1/admin/*` are refused; Homeport calls reload directly when config changes.
